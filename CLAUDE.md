# Navexa AgeCheck for WooCommerce: agent notes

The plan is §5 of `~/.cache/agecheck-gap-2026-11-13/design-final.md` (layout, milestones W0-W5, hooks table); `owner-decisions.md` next to it overrides it. The engine contract is the tax repo's `proto/agecheck/v1/verification.proto` at origin/main (E3, E9, E4a, E10a are in tax v0.0.163/164) and its CLAUDE.md (AgeCheck sections); keep `tests/mock-agecheck/server.mjs` in step with that proto, not with the plan. README.md has the commands.

## Rules
- **Fail closed.** Any `ConnectError`, a missing key, an unknown mode or a paused install refuses: never admit, never release. There is no fail-open setting.
- **Server decides.** Admission needs `GetVerification` PASSED with a clearing pass class; release needs `GetClearance` CLEARED. Both go through `Mode::accepts_livemode()`, and release also through `Mode::may_auto_release()`. Browser-sent ids are hints only.
- **No PII or secrets in logs.** Use `Client::log()` with ids and codes only. Never log a key, a request body, `ConnectError::server_message()` or a hosted URL.
- **Request paths make one attempt, with no sleeps.** Action Scheduler jobs reschedule on `ConnectError::is_retryable()` after `retry_after()`. A bodiless 500 or Cloudflare 520-526 reads as `unavailable` (retryable); a Connect body's own code always wins.
- **HPOS only.** Use `wc_get_order`, order CRUD meta and `wc_get_orders`. Never post meta or `WP_Query` on orders.
- **Names.** Options are `navexa_agecheck_*`, order meta `_navexa_agecheck_*`, hooks `navexa_agecheck_*`, namespace `Navexa\AgeCheck`, text domain `navexa-agecheck-for-woocommerce`.
- **Settings loads only on WooCommerce settings screens.** `Settings` extends `WC_Settings_Page`, so never reference it from checkout code; use `Options`.
- **Site address is `Install::home()`** (the raw `home` option, which still honours `WP_HOME`), never `home_url()`. Multilingual plugins (TranslatePress, WPML) filter `home_url` per request on the front end only, so a fingerprint or origin built from it pauses checkout while admin screens look fine.
- **Order external ids** are `wc:{install_id}:{blog_id}:{order_id}`. They are stored in order meta at bind and never recomputed, because `Install::confirm_site()` rotates the install_id.
- **`add_option()` is not a mutex.** WordPress runs `INSERT ... ON DUPLICATE KEY UPDATE` after a read, so two racing writers both "win". Locks and webhook dedupe need an atomic primitive, such as a plain `INSERT` into a plugin table with a unique key, or `$wpdb->query( "INSERT IGNORE ..." )` and a check of rows affected.

## Holds (W1)
- **Only this plugin leaves `wc-agecheck-hold`.** The backstop (`woocommerce_before_order_object_save`) refuses every exit except cancelled, refunded, failed and trash; `Hold::release()` sets a per-order flag so its own save passes. Release only orders with `_navexa_agecheck_held=yes`.
- **GetClearance spends the clearance.** Ask it only for an order in the hold, store the key on the order before the call (`save_meta_data()` first), reuse it until an answer is recorded, rotate after HOLD/DENIED. DENIED `replayed` means released, never denied.
- **Required is sticky.** `Requirement::is_required()` never turns a stored `yes` back to `no`. Unknown counts as required. Local pickup (owner Q11c) is the only shipping-method exemption, and it has one list: `Requirement::pickup_method_ids()` (WooCommerce's local-pickup methods plus `PICKUP_METHODS`, through `navexa_agecheck_pickup_methods`). The hold path (`is_pickup()`) and the pre-payment gate (`cart_is_pickup()`) both read it; pickup is neither verified nor held.
- **The webhook only queues a release run.** Never act on a webhook body's state; the run asks GetClearance.
- **External ids are never minted while paused** (`Binding::external_id()`), so a copied site cannot reuse the original install_id.
- **Order meta is copyable.** Duplicate-order plugins, imports and WooCommerce Subscriptions (parent to subscription to renewal) copy `_navexa_agecheck_*`. Record a release only with `Meta::mark_released()`: `Meta::is_released()` trusts it only on the order it names (`RELEASED_FOR`). `Binding::forget_foreign()` drops state whose external id names another order (every `external_id()` call and every release run). Read an external id for an RPC through `Binding::external_id()` or `owned_external_id()`, never the raw meta.
- **Never pass `$unique = true` to Action Scheduler.** Before AS 4.0 (WooCommerce 9.9 bundles 3.9.2) it matches hook and group only, so one order's pending action silently drops every other order's. Use `Release::queue_once()` (args-aware, pending only).
- **Verification links only for `BOUND_BY=create`** (owner Q7: emailed links need document_name_check REQUIRED). Checkout (attach) and adopted verifications are never emailed.
- **Store API order-pay saves before it validates**, and the guard reverts the ship-to in that save, so `Checkout\OrderPay` reads `AddressGuard::ship_to_change_requested()`, not unsaved changes. `woocommerce_checkout_validate_order_before_payment` has two owners: `Checkout\Blocks::validate()` decides the order a Store API cart checkout is placing (`Blocks::is_cart_checkout()`, which may be a reused pending/failed order), `Checkout\OrderPay::validate_existing_order()` every other existing order. Each skips the other's.
- **Unit tests** use the `WC_Order` stand-in in `tests/phpunit/stubs.php` (`WC_Order::make()`, `$order->meta`, `$order->notes`, `set_shipping_*()`); `wire_order_hooks()` runs the backstop, the guard and the hold-entry action on `save()`, since Brain Monkey never runs added hooks. `FakeWpdb` understands exactly `Lock`'s and `RateLimit`'s SQL and throws on any other options-table statement.

## Pre-payment (W2)
- **The browser holds nothing that admits an order.** The verification id and the checkout guard live in the WooCommerce session (`Checkout\Session`); the start/refresh answer carries only `{v, status, hosted_url?, message?}`. Never put a vid, guard or key in the page, the cart data or a log line (log `vid=` ids and verdict codes only; never the hosted URL, the sid or an address).
- **One address normalizer: `OrderAddress::normalize()`.** Every address the engine sees goes through it: the checkout's `intended_ship_to` (`ShipTo::from_customer()`/`from_checkout_data()`), the order's `ship_to` (`OrderAddress::ship_to()`, also `ShipTo::from_order()`), and the identity's residential address. `OrderAddress::ship_to_type()` is the shipping address whenever the order needs one or any shipping field is filled in, and billing only when the shipping address is wholly empty: an order with no shipping line (staff-created, REST, POS, imported) can still carry a full shipping address, and that is where it ships. An incomplete shipping address is never replaced by billing (null: review, or a refused checkout). For cart checkouts this equals `ShipTo::from_customer()` (shipping when the cart needs a shipping address, else billing), because a cart that needs none leaves the order's shipping empty (classic) or a copy of billing (Store API), so the intended ship-to and the order's ship-to never differ for the same address, or AttachOrder answers `ship_to_changed`. Compare with `ShipTo::mac()`/`equals()`/`hash()`; `ShipTo::engine_canonical()` is the one canonical form (`OrderAddress::hash()` uses it), pinned byte for byte by `tests/phpunit/fixtures/ship-to-vectors.json`, exported from the engine; regenerate it from the engine if `ShipToCanonical` changes, never edit it by hand.
- **Rate limits key on the WooCommerce customer id**, not the sid: concurrent first starts each mint their own sid (found in wp-env). The counter table is the only rate-limit store; never a transient or `add_option()`. Counter keys and the recent-start IP fingerprints are HMACs keyed from the guard secret, never plain hashes (IPv4 is brute-forceable). A missing table or secret answers `RateLimit::UNAVAILABLE` ("temporarily unavailable"), never "too many attempts".
- **Checkout to order hand-off.** The guarded verification's id sits alone in the session key `navexa_agecheck_vid` (`Session::KEY_VID`, set and cleared with the guard `Session::KEY_GUARD`). `Binding::bind_checkout()` (on `woocommerce_checkout_order_processed` / `woocommerce_store_api_checkout_order_processed`) binds only the verification the gate admitted in the same request (`Gate::admitted_verification_id()`, which must also be `KEY_VID`), never `KEY_VID` alone: it outlives the guard's TTL and is not tied to the order's ship-to. Store API order-pay (the same hook, no gate), accept-and-hold mode and orders placed without the gate therefore take the order-bound create + link path (Q11b). It records the verification on the order as `Meta::VERIFICATION_ID` with `Meta::SHIP_TO_HASH` (`OrderAddress::hash()` of the order's ship-to), calls `Session::forget_verification()`, then `AttachOrder`. A resumed bound order is admitted only at its `SHIP_TO_HASH` (`Gate::is_bound_ship_to()`); without one it is refused and dropped. A bound order whose ship-to changed is dropped with `Session::forget_verification_of($vid)`, so a check the shopper already passed for the new ship-to survives. Which carts and orders need a check is `Requirement` (`cart_required()`, `is_required()`); there is no filter that turns a check off. The pre-payment gate decides the Store API draft with `Requirement::evaluate()`, which records nothing: WooCommerce saves a refused draft and reuses it whatever the cart holds next, so a sticky `REQUIRED` written there would keep gating it after the shopper removed the restricted items or chose pickup. A reused draft already bound always goes through the gate (its bound ship-to).
- Built assets (`assets/js/`, `assets/build/`) are committed and CI rebuilds them: run `npm run build` after touching `assets/src/`.

## Style
- WordPress Coding Standards (`phpcs.xml.dist`): long array syntax, Yoda conditions, snake_case methods, a docblock on everything. PHP 7.4 syntax only. `includes/` is PSR-4, so the WordPress file-name sniff is off there.
- Tests are Brain Monkey unit tests in `tests/phpunit/Unit` (in-memory options, transients, HTTP, WC session/cart/customer and a counter-table `wpdb` in `TestCase`), plus `tests/wp-env/smoke.php` and `tests/wp-env/prepayment.mjs` for behaviour that only real WooCommerce shows, and `tests/e2e/prepayment-browser.mjs` for the popup. The mock engine (`tests/mock-agecheck/server.mjs`) gains RPCs as milestones need them. Keep its answers proto3 JSON: lowerCamelCase, zero values omitted.
- Docker for PHP (`php:8.3-cli`, `php:7.4-cli`, `composer:2`) with `-u "$(id -u):$(id -g)"`.
