# Navexa AgeCheck for WooCommerce: agent notes

The plan is §5 of `~/.cache/agecheck-gap-2026-11-13/design-final.md` (layout, milestones W0-W5, hooks table); `owner-decisions.md` next to it overrides it. The engine contract is the tax repo's `proto/agecheck/v1/verification.proto` at origin/main (E3, E9, E4a, E10a are in tax v0.0.163/164; E8c links and E12a reuse at d6dead63, both flags off in production) and its CLAUDE.md (AgeCheck sections); keep `tests/mock-agecheck/server.mjs` in step with that proto, not with the plan. README.md has the commands.

## Rules
- **Fail closed.** Any `ConnectError`, a missing key, an unknown mode or a paused install refuses: never admit, never release. There is no fail-open setting.
- **Server decides.** Admission needs `GetVerification` PASSED with a clearing pass class; release needs `GetClearance` CLEARED. Both go through `Mode::accepts_livemode()`, and release also through `Mode::may_auto_release()`. Browser-sent ids are hints only.
- **No PII or secrets in logs.** Use `Client::log()` with ids and codes only. Never log a key, a request body, `ConnectError::server_message()` or a hosted URL.
- **Request paths make one attempt, with no sleeps.** Action Scheduler jobs reschedule on `ConnectError::is_retryable()` after `retry_after()`. A bodiless 500 or Cloudflare 520-526 reads as `unavailable` (retryable); a Connect body's own code always wins.
- **HPOS only.** Use `wc_get_order`, order CRUD meta and `wc_get_orders`. Never post meta or `WP_Query` on orders.
- **Names.** Options are `navexa_agecheck_*`, order meta `_navexa_agecheck_*`, hooks `navexa_agecheck_*`, namespace `Navexa\AgeCheck`, text domain `navexa-agecheck-for-woocommerce`.
- **Settings loads only on WooCommerce settings screens.** `Settings` extends `WC_Settings_Page`, so never reference it from checkout code; use `Options`.
- **Site address is `Install::home()`** (the raw `home` option, which still honours `WP_HOME`), never `home_url()`. Multilingual plugins (TranslatePress, WPML) filter `home_url` per request on the front end only, so a fingerprint or origin built from it pauses checkout while admin screens look fine.
- **Order external ids** are `wc:{install_id}:{blog_id}:{order_id}`. They are stored in order meta at bind and never recomputed, because `Install::confirm_site()` rotates the install_id.
- **`add_option()` is not a mutex.** WordPress runs `INSERT ... ON DUPLICATE KEY UPDATE` after a read, so two racing writers both "win". Locks and webhook dedupe need an atomic primitive, such as a plain `INSERT` into a plugin table with a unique key, or `$wpdb->query( "INSERT IGNORE ..." )` and a check of rows affected.

## Holds (W1)
- **Only this plugin leaves `wc-agecheck-hold`.** The backstop (`woocommerce_before_order_object_save`) refuses every exit except cancelled, refunded, failed and trash; `Hold::release()` sets a per-order flag so its own save passes. Release only orders with `_navexa_agecheck_held=yes`.
- **GetClearance spends the clearance.** Ask it only for an order in the hold, store the key on the order before the call (`save_meta_data()` first), reuse it until an answer is recorded, rotate after HOLD/DENIED. DENIED `replayed` means released, never denied.
- **Required is sticky.** `Requirement::is_required()` never turns a stored `yes` back to `no`. Unknown counts as required. Local pickup (owner Q11c) is the only shipping-method exemption, and it has one list: `Requirement::pickup_method_ids()` (WooCommerce's local-pickup methods plus `PICKUP_METHODS`, through `navexa_agecheck_pickup_methods`). The hold path (`is_pickup()`) and the pre-payment gate (`cart_is_pickup()`) both read it; pickup is neither verified nor held.
- **The webhook only queues a release run.** Never act on a webhook body's state; the run asks GetClearance.
- **External ids are never minted while paused** (`Binding::external_id()`), so a copied site cannot reuse the original install_id.
- **Order meta is copyable.** Duplicate-order plugins, imports and WooCommerce Subscriptions (parent to subscription to renewal) copy `_navexa_agecheck_*`. Record a release only with `Meta::mark_released()`: `Meta::is_released()` trusts it only on the order it names (`RELEASED_FOR`). `Binding::forget_foreign()` drops state whose external id names another order (every `external_id()` call and every release run). Read an external id for an RPC through `Binding::external_id()` or `owned_external_id()`, never the raw meta.
- **Never pass `$unique = true` to Action Scheduler.** Before AS 4.0 (WooCommerce 9.9 bundles 3.9.2) it matches hook and group only, so one order's pending action silently drops every other order's. Use `Release::queue_once()` (args-aware, pending only).
- **Verification links only for `BOUND_BY=create`** (owner Q7: emailed links need document_name_check REQUIRED). Checkout (attach) and adopted verifications are never emailed (W3 PR 12 below).
- **Store API order-pay saves before it validates**, and the guard reverts the ship-to in that save, so `Checkout\OrderPay` reads `AddressGuard::ship_to_change_requested()`, not unsaved changes. `woocommerce_checkout_validate_order_before_payment` has two owners: `Checkout\Blocks::validate()` decides the order a Store API cart checkout is placing (`Blocks::is_cart_checkout()`, which may be a reused pending/failed order), `Checkout\OrderPay::validate_existing_order()` every other existing order. Each skips the other's.
- **Unit tests** use the `WC_Order` stand-in in `tests/phpunit/stubs.php` (`WC_Order::make()`, `$order->meta`, `$order->notes`, `set_shipping_*()`); `wire_order_hooks()` runs the backstop, the guard and the hold-entry action on `save()`, since Brain Monkey never runs added hooks. `FakeWpdb` understands exactly `Lock`'s and `RateLimit`'s SQL and throws on any other options-table statement.

## Pre-payment (W2)
- **The browser holds nothing that admits an order.** The verification id and the checkout guard live in the WooCommerce session (`Checkout\Session`); the start/refresh answer carries only `{v, status, hosted_url?, message?}`. Never put a vid, guard or key in the page, the cart data or a log line (log `vid=` ids and verdict codes only; never the hosted URL, the sid or an address).
- **One address normalizer: `OrderAddress::normalize()`.** Every address the engine sees goes through it: the checkout's `intended_ship_to` (`ShipTo::from_customer()`/`from_checkout_data()`), the order's `ship_to` (`OrderAddress::ship_to()`, also `ShipTo::from_order()`), and the identity's residential address. `OrderAddress::ship_to_type()` is the shipping address whenever the order needs one or any shipping field is filled in, and billing only when the shipping address is wholly empty: an order with no shipping line (staff-created, REST, POS, imported) can still carry a full shipping address, and that is where it ships. An incomplete shipping address is never replaced by billing (null: review, or a refused checkout). For cart checkouts this equals `ShipTo::from_customer()` (shipping when the cart needs a shipping address, else billing), because a cart that needs none leaves the order's shipping empty (classic) or a copy of billing (Store API), so the intended ship-to and the order's ship-to never differ for the same address, or AttachOrder answers `ship_to_changed`. Compare with `ShipTo::mac()`/`equals()`/`hash()`; `ShipTo::engine_canonical()` is the one canonical form (`OrderAddress::hash()` uses it), pinned byte for byte by `tests/phpunit/fixtures/ship-to-vectors.json`, exported from the engine; regenerate it from the engine if `ShipToCanonical` changes, never edit it by hand.
- **Rate limits key on the WooCommerce customer id**, not the sid: concurrent first starts each mint their own sid (found in wp-env). The counter table is the only rate-limit store; never a transient or `add_option()`. Counter keys and the recent-start IP fingerprints are HMACs keyed from the guard secret, never plain hashes (IPv4 is brute-forceable). A missing table or secret answers `RateLimit::UNAVAILABLE` ("temporarily unavailable"), never "too many attempts".
- **Checkout to order hand-off.** The guarded verification's id sits alone in the session key `navexa_agecheck_vid` (`Session::KEY_VID`, set and cleared with the guard `Session::KEY_GUARD`). `Binding::bind_checkout()` (on `woocommerce_checkout_order_processed` / `woocommerce_store_api_checkout_order_processed`) binds only the verification the gate admitted in the same request (`Gate::admitted_verification_id()`, which must also be `KEY_VID`), never `KEY_VID` alone: it outlives the guard's TTL and is not tied to the order's ship-to. Store API order-pay (the same hook, no gate), accept-and-hold mode and orders placed without the gate therefore take the order-bound create + link path (Q11b). It records the verification on the order as `Meta::VERIFICATION_ID` with `Meta::SHIP_TO_HASH` (`OrderAddress::hash()` of the order's ship-to), calls `Session::forget_verification()`, then `AttachOrder`. A resumed bound order is admitted only at its `SHIP_TO_HASH` (`Gate::is_bound_ship_to()`); without one it is refused and dropped. Binding runs before payment, so after a declined card the session holds no check: `Start::state($route)` reads passed for the order a retry through that route resumes at its bound ship-to (`Gate::resumable_bound_order($ship_to, $route)`), or the block refuses Place order and the shopper pays for a second check nothing attaches (the 1.0.x defect, fixed in 1.0.4). **The state follows the route that places the order, never the union of both session keys**: the cart data (`Start::endpoint_data()`, read by the block) asks `Gate::ROUTE_STORE_API` = `bound_draft_order()` (`store_api_draft_order` by WooCommerce's `DraftOrderTrait::is_valid_draft_order()` rule), the classic button asks `Gate::ROUTE_CLASSIC` = `bound_awaiting_order()` (`order_awaiting_payment`, WooCommerce's classic resume rule), and each gate admits only its own (`Classic::validate()`, `Blocks::validate()`). The keys drift apart: WooCommerce 11.x's Store API also writes `order_awaiting_payment` (9.9 does not), `Blocks::validate()` drops only `store_api_draft_order`, `Classic::validate()` only `order_awaiting_payment`; reading both showed passed for an order the route would not place (a dead end: no Verify age, Place order refused). With both checkout pages in one session, a block decline then the classic page needs a new check on 9.9 (classic makes a new order) and resumes the draft on 11.x. A bound order whose ship-to changed is dropped with `Session::forget_verification_of($vid)`, so a check the shopper already passed for the new ship-to survives. Which carts and orders need a check is `Requirement` (`cart_required()`, `is_required()`); there is no filter that turns a check off. The pre-payment gate decides the Store API draft with `Requirement::evaluate()`, which records nothing: WooCommerce saves a refused draft and reuses it whatever the cart holds next, so a sticky `REQUIRED` written there would keep gating it after the shopper removed the restricted items or chose pickup. A reused draft already bound always goes through the gate (its bound ship-to).
- **Data-match identity (E5).** The pre-payment start sends `identity = {name, residentialAddress}` (billing first + last name, the billing address through `OrderAddress::normalize()`) only as a pair, only for a complete US billing address, and only when that address is the ship-to by the engine's eligibility comparison (`OrderAddress::same_residence()`, never stricter than `domain.sameResidence`) (`Start::identity()`); otherwise no identity: billing elsewhere is never data-eligible, so the name and address would be personal data AgeCheck cannot use. Names are whitespace-collapsed with `OrderAddress::collapse()` (the engine trims Unicode whitespace). Never a DOB. A guest's billing email only while GetIntegrationInfo's `guest_reuse_code` (the engine decides; never restate its rule here) is true (`Start::guest_email()`, TAX-1839: the returning-guest emailed code), never for a signed-in customer (customer_ref), with `:e{16 hex}` (HMAC under a guard-secret key) on the start's idempotency key, retried once without it on `invalid_argument`; never logged. `document_name_check` stays NONE pre-order (sent explicitly: unset with a name means REQUIRED); order-bound creates stay REQUIRED with the billing name. Classic copies the typed billing name and email into the session (`Classic::remember_billing_name()`).
- Built assets (`assets/js/`, `assets/build/`) are committed and CI rebuilds them: run `npm run build` after touching `assets/src/`.

## Links and reuse (W3 PRs 12, 14)
- **The engine decides whether a link is emailed** (`Links`, `EngineLinkSender`); `NAVEXA_AGECHECK_EMAIL_LINKS` is only a kill switch (`false` = `DisabledLinkSender`, no call). A release run asks once per verification, and only while it waits at the hosted page (`Links::HOSTED_STATES`: never `created`, which the engine refuses as final). Store the idempotency key (`Meta::LINK_KEY`) and `save_meta_data()` before the call; reuse it until an answer is recorded; drop it after any recorded answer, a refusal included.
- **Refusals are told apart by the engine's sentinel text** (`EngineLinkSender::refusal()`; read `server_message()` there, never log it). Links off, no display name and no RPC are store-wide: `Links::OPTION_BLOCK`, one call an hour store-wide (`BLOCK_TTL`), the order polled every six hours, `Admin\Notices::links_text()`. Never add a path that asks SendVerificationLink per order while a block stands (a retry storm); staff resends ignore it on purpose. RESOURCE_EXHAUSTED "verification links sent" is the 5-in-24h budget, nothing sent; any other RESOURCE_EXHAUSTED is the key's rate limit (rethrow, retryable).
- **Staff link actions take the release run's lock** (`Release::lock_name()`) and re-read the order; Order actions check `manage_woocommerce` and `woocommerce_meta_nonce` again.
- **Return URLs never carry the order key.** AgeCheck's page comes back to `OrderVerify`'s return step with the order's keyed tag (guard secret, `navexa-agecheck/order-return/v1`); it only queues a release run (rate limited) and redirects to the order page only for its own customer or the browser whose session-bound nonce started it. Send a return URL only when GetIntegrationInfo says `origin_allowed`.
- **"Verify now" start** needs the order key, a nonce whose action starts with `woocommerce` (WooCommerce ties a guest's nonce to their session only then) and, for an account's order, that customer signed in. It uses the start key for `CreateHostedSession`; the fulfilment key only through a release run, and only when the order has no verification yet. Validate the hosted URL with `Start::is_hosted_url()` before redirecting.
- **customer_ref is `CustomerRef`** (HMAC of blog and user id under a key from the guard secret), only for an authenticated customer: `get_current_user_id()` at the start, the order's `customer_id` for an order-bound create; guests none; never the raw user id, an email or a name. The start's idempotency key gains `:c{16 hex}` with it (a guest who signs in keeps the sid). Reuse is the engine's: `PASS_CLASS_REUSED` clears like any pass (the gate's deny-list `Gate::NON_CLEARING_PASS_CLASSES` admits it; release still waits for GetClearance). `Meta::PASS_CLASS` is for the panel only.
- **The mock models production by default**: `links` `off`, `reuse` `off`. Turn them `on` per test. With `reuse` on and a display name its GetIntegrationInfo answers `reuseWindowDays` and `guestReuseCode`, and its hosted page offers the emailed code only on a NONE check with an email.
- **Guest reuse (TAX-1839)**: in test mode AgeCheck emails a reuse code only to a confirmed notification recipient, so the settings line and readme say so.

## Entry age gate (W3 PR 13)
- **Self-attestation, never verification**: say so in every merchant- or readme-facing line. Off by default (`Options::ENTRY_GATE`).
- **No key, no PII, no network call on the storefront**: the minimum age and display name come from `Options::STORE_PROFILE`, which `Mode::lookup()` writes; never call `Mode::info()` from a front-end page.
- **Page-cache safe**: the server decides only whether a URL carries the gate (scope; the same for every visitor); the answer lives in the visitor's localStorage (sessionStorage for 0 days, and then only sessionStorage is read: an old localStorage answer has no age limit at 0 days) and the server never reads it. No cookie.
- Excluded: wp-admin, login, REST, AJAX, cron, feeds, embeds, robots, favicon, trackbacks, the Customizer preview and every `?wc-api=` request (the AgeCheck return page); the script skips the exit URL's page. `gate.ts` loads in the head and must never leave the page hidden on an error. Its two script tags carry `EntryGate::NO_OPTIMIZE` (Rocket Loader, LiteSpeed, WP Rocket opt-outs) so optimizers do not defer or delay them. Its style is px at the root and em inside (themes set `html{font-size:62.5%}`) and scoped under `html[data-navexa-agecheck-gate] .navexa-agecheck-gate` (buttons at 0,4,1) so theme button rules do not win; closing puts back each node's own `aria-hidden`.

## Hardening (W4)
- **Hiding express buttons is a convenience, never the enforcement.** `Express` answers each gateway's own documented filters (WooPayments, WooPay, Stripe ECE, PayPal Payments; list and spike in its docblock and README's matrix). The gates and the hold must still stop every express order. Pay-for-order is never hidden (Q11b): Stripe and WooPayments ask their cart filters about the session cart on order-pay, so `supported_for_cart()` answers as the gateway decides there. PayPal on the classic checkout is the payment method behind `WC_Checkout` validation, so it is left alone. Pickup does not bring buttons back (the wallet sheet can change the shipping method). PayPal Payments 4.2 defaults to its SDK v6 stack, which never asks v5's "disabled" filters: classic pages are covered by taking over the renderer hooks both stacks share (forwarded at render time, `Express::paypal_proxy()`), block pages by `buttons_enabled` and the wallets' `styles` in the blocks data filter.
- **Turnstile guards start only**, after the rate limits and before any AgeCheck call; off by default; on without both keys, or Cloudflare not answering, is `unavailable`; never log the token or the secret. The widget is rendered inside the async start (after the popup opened), never before the click. An interactive challenge shows on the checkout page, not in the popup, so the start gives up at once (`challenging()`: popup closed, "complete the security check shown", focus on the widget's group, nothing sent to the store, no rate-limit hit) and the solved challenge's token is kept for the next click.
- **Uninstall runs without the plugin.** `includes/Uninstall.php` names everything literally and uses no other plugin class (the autoloader is not loaded); `UninstallTest` checks that. Held orders move to On hold only with the hold status registered for the move (otherwise WooCommerce reads it as "pending" and emails the shopper). Order and product meta go only with "Delete data on uninstall". In wp-env run `w4-uninstall.php` with `--skip-plugins=navexa-agecheck-for-woocommerce`, never `wp plugin uninstall`/`delete` (the plugin directory is the checkout).
- **The privacy eraser keeps the release state** (`STATUS`, `RELEASED_FOR`, `REQUIRED`) and skips held, refund-pending and still-shippable orders (any status but completed, cancelled, refunded, failed, trash: the verification id is what locks the ship-to); it erases only what links an order to the shopper's AgeCheck record, and only when WooCommerce's own order-erasure setting allows. It must run before WooCommerce's order eraser, which anonymizes the email and customer id orders are found by: registered at priority 5, and also on `woocommerce_privacy_before_remove_order_personal_data` (WooCommerce's eraser, bulk "Remove personal data", retention cleanup). `AddressGuard` lets WooCommerce's own anonymization of the ship-to through (`erasure_starts`/`erasure_ends`); never undo it.
- **Strings**: after changing any translatable string, regenerate `languages/navexa-agecheck-for-woocommerce.pot` (command in README); `I18nTest` fails on a PHP string missing from it. JS copy comes from PHP (`Frontend::script_data()`), editor strings use `@wordpress/i18n`.
- **Button accessibility**: keep `aria-disabled` (not `disabled`) while busy, the classic live region outside the replaced fragment, and the focus return after a check the shopper started (`a11y.ts`, the block's focus effect); `tests/e2e/prepayment-browser.mjs` checks them in three engines.

## Link withdrawal and release (W5)
- **Closing an order withdraws its links, never in the status change.** `LinkRevoke` hooks `woocommerce_order_status_changed` (cancelled, refunded, failed), `woocommerce_order_fully_refunded` (a full refund whatever status a filter kept; a partial refund withdraws nothing), `woocommerce_trash_order` and `trashed_post` (the posts table's own Orders screen calls `wp_trash_post()` directly), and `woocommerce_before_delete_order` + `before_delete_post` for a deletion (the order and its meta are gone before the run, so that action's args carry `[order, attempt, vid, key]`; a request-level guard stops the posts table queueing it twice). The hook records `REVOKE=pending:{vid}` with `REVOKE_AT` (pending since) on a freshly read order (never the object WooCommerce passed: `wc_create_refund()` saves a stale copy) and queues one action; it catches every `Throwable`. Only for an order's own verification (`Binding::owned_external_id()`) under the current install_id (`LinkRevoke::same_install()`: a confirmed copied site must not withdraw the original's links), with a link on record as possibly open, or held by the plugin on a verification that is not a checkout one (`BOUND_BY=attach` passed before the order and is never emailed).
- **The run is a release-style job**: the order's lock (`Release::lock_name()`), the key `rvk:{vid}:{random}` saved before the call and reused until an answer is recorded, retries with backoff and Retry-After (`MAX_ATTEMPTS`, then recorded as failed), a reopened order skipped unless a call was already made. Never mark a link withdrawn without AgeCheck's answer. Any other `Throwable` in a run is retried like an outage, and `Sweep` calls `LinkRevoke::requeue_stale()` for withdrawals pending longer than `REQUEUE_AFTER` (renewing the stamp): never leave `pending` without a way out, since `Privacy` keeps the order's data while it is pending. `Links::STATE_REVOKED` is final for release runs only while `LinkRevoke::is_closed()`; an order held again gets a new link (staff may always resend).
- `WC_Order::delete()` sets the object's id to 0: keep the id before trashing in tests.
- **Release tooling**: `bin/build-zip.sh` (git archive + export-ignore, an allowlist of runtime files, version and changelog checks, deterministic zip, SHA256SUMS), `bin/verify-zip.sh` (throwaway wp-env with only the zip mapped; never install a zip into the checkout-mapped env: `wp plugin install --force` would overwrite the checkout), `.github/workflows/release.yml` (v* tag on main, draft release only). A new file at the repository root needs `export-ignore` or a place in build-zip.sh's allowlist. wordpress.org SVN is a manual, owner-approved step after AgeCheck `open`.

## Style
- WordPress Coding Standards (`phpcs.xml.dist`): long array syntax, Yoda conditions, snake_case methods, a docblock on everything. PHP 7.4 syntax only. `includes/` is PSR-4, so the WordPress file-name sniff is off there.
- Tests are Brain Monkey unit tests in `tests/phpunit/Unit` (in-memory options, transients, HTTP, WC session/cart/customer and a counter-table `wpdb` in `TestCase`), plus `tests/wp-env/smoke.php` and `tests/wp-env/prepayment.mjs` for behaviour that only real WooCommerce shows (`tests/wp-env/mu-plugins/`, mapped to `wp-content/mu-plugins` by `.wp-env.json`, adds `navexa_test_decline`, a gateway that always declines, for the payment-retry groups), and `tests/e2e/prepayment-browser.mjs` for the popup. The mock engine (`tests/mock-agecheck/server.mjs`) gains RPCs as milestones need them. Keep its answers proto3 JSON: lowerCamelCase, zero values omitted.
- Docker for PHP (`php:8.3-cli`, `php:7.4-cli`, `composer:2`) with `-u "$(id -u):$(id -g)"`.
